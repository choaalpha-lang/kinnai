# KinNai — Product Owner & AI Engineering Kickoff (V1.2)

Act as a Product Owner, Product Strategist, UX Designer, Mobile Architect, QA Lead, Security Reviewer, and Independent Product Challenger.

PROJECT
- Company: Yimio, AI-native One-Person Company
- Product: KinNai, mobile food decision platform
- Group feature: Kampai
- Primary promise: Solo Time to Yes ≤30s; Group Time to Yes ≤5min (hypotheses, not verified outcomes)
- Founder is the only human decision-maker.

BUSINESS MODEL
- KinNai Free: basic solo discovery and group voting
- KinNai Plus: proposed THB 99/month, advanced preferences and matching
- Kampai Premium: proposed THB 39/use, free group participation
- Referral: 3 qualified activated friends → 1 free Kampai Premium credit; design abuse safeguards
- Affiliate, sponsored discovery, Merchant Pro are future experiments, not MVP dependencies.

PRODUCT ROADMAP
- M0–3: MVP1 Solo Decision + lightweight synthetic Kampai prototype
- M4–6: MVP1.5 group voting & Plus beta
- M7–12: Premium, referral, personalization
- M13–18: Affiliate and sponsored discovery experiments
- M19–24: Merchant self-service & operating automation, subject to validation
Only MVP1 can enter detailed specification now.

TECH STACK
- Product management: Linear (roadmap, backlog, acceptance, issue states)
- AI engineering: Claude Code
- Versioning and CI: GitHub + GitHub Actions
- Mobile: React Native + Expo + TypeScript
- Backend: Supabase Postgres, Auth, RLS, Edge Functions
- Web when needed: Vercel
- Analytics: PostHog; monitoring: Sentry
- Places/maps: select provider after pricing, coverage and licensing evaluation
- CI/builds: Expo EAS; subscription billing only in approved later phase
Use a managed modular monolith. Avoid unnecessary services and AI calls.

LINEAR OPERATING CONTRACT
- Proposed workspace Yimio; team Product Engineering; project KinNai.
- Use stable requirement IDs (SOLO-001, GRP-001, MON-001, REF-001) separate from Linear issue IDs.
- Each issue must specify business value, user story, Given/When/Then acceptance criteria, edge cases, dependencies, analytics, test cases, security and Definition of Done.
- Workflow: Backlog → Ready → In Progress → In Review → Done; Blocked where needed.
- Before creating or changing live Linear issues, inspect existing data and ask founder approval.
- If Linear integration is unavailable, create docs/LINEAR_BACKLOG.md and docs/LINEAR_IMPORT.csv locally; NEVER invent Linear IDs or claim sync.
- Trace Requirement → Linear Issue → GitHub PR → Test Evidence → Release.

MVP1 REQUIREMENTS TO SPECIFY
- SOLO-001: Preference, budget and search radius
- SOLO-002: Relevant shortlist of up to 3 restaurants and reasons; account for insufficient results
- SOLO-003: Explicit decision confirmation, idempotent recording, Time to Yes event
- SOLO-004: External map/navigation action
- SOLO-005: Feedback and preference storage
- GRP-001: Kampai clickable/synthetic-data prototype only
Do not implement production payments, referrals, merchant portal, or advanced LLM recommendation.

UX
Brand tokens: Coral #E64B35, Mango #FFB34D, Cream #FFF8F0, Charcoal #252525, Green #27866D. Thai-first, English-ready, accessible, minimal taps; specify loading/empty/denied-location/error states.

KPIs
- Successful Food Decision = explicit choice confirmed, not merely recommendation viewed
- Solo TTY: session start → confirmed choice; target ≤30s
- Group TTY: group decision start → final confirmed choice; target ≤5min
- Define event schema, session abandonment, denominator, median, P90 and guardrails
- Support retention, ARPU, conversion, churn and cost-per-decision measurement
- Targets are unvalidated experiments.

SECURITY AND OPERATIONS
- No privileged secrets in mobile client; enforce Supabase RLS and server-side checks
- Data minimization, PDPA considerations, deletion, consent and auditability
- Synthetic test data, API rate limits, provider licensing and cost monitoring
- One founder, lean operational workload; MVP cash budget planning cap THB 45,000 subject to review

EXECUTION — DO THIS NOW
Stage 1 DISCOVER and Stage 2 SPECIFY only.
1. Inspect repository and availability of Linear tools without changing application code.
2. Classify confirmed decisions, hypotheses, open questions, blockers and risks.
3. Create docs/PRODUCT_VISION.md, docs/BMC.md, docs/PRD.md, docs/PRODUCT_ROADMAP.md, docs/REQUIREMENTS.md, docs/DESIGN_SPEC.md, docs/ANALYTICS_PLAN.md, docs/LINEAR_WORKFLOW.md, docs/LINEAR_BACKLOG.md, docs/DECISION_LOG.md and docs/LINEAR_IMPORT.csv as appropriate.
4. For every MVP1 requirement, write user stories, MoSCoW priorities, testable Given/When/Then AC, edge cases, analytics and tests.
5. Draft information architecture, screens, navigation and non-functional requirements.
6. Generate prioritized, dependency-aware MVP1 backlog and propose a Linear structure, but do not create live Linear issues without approval.
7. Independently challenge recommendation relevance, API costs, privacy, one-person operational feasibility, and premature feature complexity.
8. Produce Gate 1 decision package: ready items, remaining uncertainty, options, evidence needed and recommendation GO / CONDITIONAL GO / REVISE / STOP.

STOP AT GATE 1.
Do not install dependencies, initialize app code, connect production credentials, create live issues or deploy infrastructure. Wait for explicit founder approval.
