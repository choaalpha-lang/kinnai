# SPIKE-001 — ประเมิน Places provider

วันที่: 2026-11-25 · ผู้จัดทำ: Claude Code · ผู้ตัดสิน: Founder · เกี่ยวข้อง: Q-001, R-001, R-002, F-01, F-03, PLAT-003

## 1. Executive Summary

- **ข้อเสนอ: ทดสอบ Google Places API (New) เป็นตัวหลัก เทียบกับ Foursquare และ Longdo** ด้วยข้อมูลจริงก่อนตัดสิน ยังไม่ควรล็อก provider จากเอกสารอย่างเดียว
- **ความครอบคลุมร้านในไทยยังเป็น UNKNOWN ทุกราย** spike นี้ทำได้เฉพาะส่วนเอกสาร (desk research) ส่วนทดสอบข้อมูลจริงต้องมี API key และพื้นที่เปิดตัว (Q-005)
- **ไม่มี provider ใดรับรองราคาต่อหัวเป็นบาทสำหรับร้านทุกประเภท** Google มี `priceRange` (ช่วงราคาเป็นสกุลเงิน) แต่ร้านไหนมีข้อมูลนี้บ้างในไทย UNKNOWN ส่วน Foursquare ให้แค่ระดับ 1–4 และ OSM ไม่มีข้อมูลราคา F-01 ยังเป็นความเสี่ยงสูง
- **ต้นทุน Google ตามราคาประกาศ:** ฟิลด์ที่ KinNai ต้องใช้ (rating, ราคา, เวลาเปิด) ทำให้คำขอถูกคิดเป็นระดับ Enterprise ที่ USD 35 ต่อ 1,000 คำขอ (ฟรี 1,000 คำขอต่อเดือน) สถานการณ์สมมติ 100 ผู้ทดสอบอยู่ที่ราว USD 35–105 ต่อเดือน
- **ข้อจำกัดของ spike นี้:** เข้าอ่านหน้าเอกสารทางการโดยตรงไม่ได้ (การดึงหน้าเว็บล้มเหลวที่ระดับ DNS แม้เพิ่มโดเมนเข้า allowlist แล้ว) ข้อมูลทั้งหมดมาจากข้อความที่เครื่องมือค้นหาดึงจากหน้าทางการ จึงมีหลายจุดที่แหล่งข้อมูลขัดกันและต้องอ่านหน้าจริงซ้ำก่อนเซ็นสัญญา

ระดับหลักฐานที่ใช้ในเอกสารนี้: **[V]** ข้อความจากหน้าทางการของผู้ให้บริการ (ผ่านผลค้นหา ยังไม่ได้อ่านทั้งหน้า) · **[C]** แหล่งข้อมูลขัดกัน · **[U]** UNKNOWN

## 2. เกณฑ์ประเมิน (ตามที่ตั้งไว้ใน Gate 1 §5)

1. ความครอบคลุมร้านในพื้นที่เปิดตัว รวมร้านข้างทาง
2. มีข้อมูลราคา เวลาเปิด ประเภทอาหาร
3. เงื่อนไขการ cache และการแสดงผล
4. ราคาต่อคำขอและโควตาฟรี
5. ใช้คู่กับแผนที่อื่นได้หรือไม่ (KinNai ไม่ฝังแผนที่ ส่งผู้ใช้ไปแอปแผนที่ภายนอก)

## 4. Finding หลัก (5C)

### SP-01 — ไม่มี provider ที่รับรองตัวกรองงบเป็นบาทได้ (สูง)

- **Condition:** ต้นแบบกรองด้วยราคาบาทต่อคน (D-002 งบเป็นเพดาน) แต่ข้อมูลจาก provider มีสามแบบ: ช่วงราคาเป็นสกุลเงินแต่ไม่ครบทุกร้าน (Google), ระดับ 1–4 (Foursquare), หรือไม่มี (Longdo, OSM)
- **Criteria:** SOLO-001/002 ต้องกรองตามงบและแสดง "ประมาณ ฿X ต่อคน" ห้ามเดาราคา (DESIGN_SPEC §5)
- **Cause:** ข้อมูลราคาร้านข้างทางในไทยเป็นข้อมูลที่ผู้ใช้หรือเจ้าของร้านกรอก ไม่ได้มาจากระบบ POS
- **Effect:** ร้านเกินงบหลุดเข้ามา หรือร้านราคาถูกที่ไม่มีข้อมูลถูกตัดออก
- **Recommendation:** ทดสอบสัดส่วนร้านที่มีข้อมูลราคาในพื้นที่เปิดตัว (เกณฑ์ใน §7) ถ้าต่ำ ให้ใช้ชั้นข้อมูลของ KinNai เอง: เก็บ `place_id` กับ **ระดับราคาที่ KinNai กำหนดเอง** (ตัวเลือกงบ 4 ระดับเดิม) โดยเริ่มจากร้านที่ Founder และผู้ทดสอบคัดไว้ แล้วปรับจากปุ่ม "แพงไป" ใน SOLO-005 วิธีนี้สอดคล้องกับกฎที่เก็บ `place_id` ได้ไม่จำกัดเวลา แต่ห้ามคัดลอกเนื้อหาอื่นของ Google ไปเก็บ

### SP-02 — ต้นทุนเกิดจากฟิลด์ที่ขอ ไม่ใช่จำนวนร้านที่ได้ (กลาง)

- **Condition:** ฟิลด์ `rating`, `priceRange`, `priceLevel`, `regularOpeningHours` ทำให้ Nearby Search คิดเป็น Enterprise ทั้งคำขอ ตามหลักว่าคิดตามฟิลด์ที่แพงที่สุดใน field mask **[V]**
- **Criteria:** Guardrail "API cost per successful decision" (ANALYTICS_PLAN §4), เพดานงบ THB 45,000 (D-009)
- **Cause:** โมเดลราคาของ Google คิดตามระดับฟิลด์
- **Effect:** ตัด `rating` ออกก็ไม่ประหยัด เพราะ `priceRange` และเวลาเปิดอยู่ระดับเดียวกัน
- **Recommendation:** ออกแบบให้ **1 การค้นหาต่อ 1 criteria** แล้วจัดอันดับและเลื่อน "ขอชุดใหม่" จากผลที่ได้มาแล้วใน session เดียวกัน ไม่ยิงคำขอใหม่ทุก reroll ตรวจก่อนว่าการเก็บผลไว้ใน session ขัดข้อกำหนดการ cache หรือไม่ (SP-03) ตั้ง daily quota และ budget alert ตั้งแต่วันแรก

### SP-03 — ข้อกำหนด cache ขัดกันทั้งใน Google และ Foursquare (กลาง)

- **Condition:** Google: หน้า policy ของ Places API ไม่ได้ระบุ lat/lng ในรายการข้อยกเว้น แต่ Service Specific Terms ให้เก็บ lat/lng ได้ 30 วัน **[C]** Foursquare: 30 วันกับ 24 ชั่วโมงขัดกัน **[C]**
- **Criteria:** PLAT-003 "cache ตามที่ license อนุญาตเท่านั้น", R-002
- **Cause:** เอกสารหลายฉบับและหลายเวอร์ชัน
- **Effect:** ถ้าตีความผิด อาจผิดสัญญาหรือจ่ายแพงเกินจำเป็น
- **Recommendation:** อ่านเอกสารฉบับปัจจุบันเต็มหน้าก่อนเลือก (ดูข้อจำกัดของ spike §1) และออกแบบแบบปลอดภัยที่สุด: เก็บถาวรเฉพาะ `place_id` กับข้อมูลที่ KinNai สร้างเอง ส่วนข้อมูลของ provider ดึงใหม่ตอนใช้

## 5. หมายเหตุรายผู้ให้บริการ

**Google Places API (New)**
- ข้อดีที่มีหลักฐาน: มีฟิลด์ช่วงราคา เวลาเปิด และคะแนนครบในคำขอเดียว
- ข้อควรระวัง: ต้องมีบัญชี Google Cloud ที่ผูกการเรียกเก็บเงิน ต้องตรวจข้อกำหนดการแสดงผล ราคาที่อ้างมาจากตารางราคาที่ปรากฏในผลค้นหา ซึ่งมีหลายเวอร์ชัน ต้องยืนยันกับหน้าราคาปัจจุบัน

**Foursquare Places API**
- ข้อดี: ราคา Pro ต่ำกว่า และมีเครดิตฟรีรายเดือน
- ข้อควรระวัง: ราคากับเวลาเปิดอยู่ในระดับ Premium ซึ่งยังไม่ทราบราคา ราคาเป็นระดับ 1–4 ไม่ใช่บาท ต้องแสดง "Powered by Foursquare" และคู่มือบางหน้าระบุตัวกรองราคาว่า "coming soon" ต้องยืนยัน

**Longdo Map**
- ข้อดี: ผู้ให้บริการไทย ข้อมูลแผนที่ไทยจาก NuMAP โควตาฟรีสูงสำหรับบริการผู้บริโภค
- ข้อควรระวัง: ฟิลด์ราคา คะแนน และเวลาเปิดที่เอกสารระบุไม่ชัด เงื่อนไขเชิงพาณิชย์อาจต้องคุยกับฝ่ายขาย

**OpenStreetMap**
- เหมาะเป็นแหล่งสำรองหรือใช้ทดสอบฟรี ไม่แนะนำเป็นแหล่งหลักสำหรับร้านอาหารในไทยโดยไม่มีการวัดความครบถ้วนก่อน (**[U]**)
- Overpass สาธารณะ: เอกสารระบุให้การใช้เชิงพาณิชย์ใช้เซิร์ฟเวอร์ที่โฮสต์เองหรือแบบเสียเงิน **[V]** จึงไม่เหมาะกับการใช้เป็น backend โดยตรง
- ODbL: ต้องแสดงที่มาและต้องแชร์ฐานข้อมูลที่ derive ต่อภายใต้ ODbL **[V]**

**HERE**
- ข้อมูลที่ได้มาขัดกันเรื่องโควตาฟรี (250,000 ธุรกรรมต่อเดือนกับตัวเลขที่เก่ากว่า) และยังไม่พบข้อมูลความครอบคลุมในไทยหรือข้อกำหนด cache จึงยังไม่ประเมินต่อ

สมมติฐาน (ไม่ใช่ข้อมูลจริง): คำขอ Nearby Search Enterprise 1 ครั้งต่อ 1 การค้นหา, ราคาประกาศช่วงแรก USD 35 ต่อ 1,000, ฟรี 1,000 คำขอต่อเดือน, ไม่มีการ cache ข้าม session

## 7. แผนทดสอบข้อมูลจริง (ส่วนที่ 2 ของ spike)

ต้องมีก่อนเริ่ม: (ก) พื้นที่เปิดตัว 1–3 ย่าน (Q-005) (ข) ผู้ทดสอบหรือ Founder ช่วยทำรายการร้านจริงย่านละ 30 ร้านที่รู้จัก รวมร้านข้างทางและร้านราคาต่ำกว่า 100 บาท เป็นเกณฑ์อ้างอิง (ground truth) (ค) API key ของ Google, Foursquare และ Longdo (ง) เพิ่มโดเมน API ของแต่ละรายเข้า allowlist ของ session

| ตัวชี้วัด | วิธีวัด | เกณฑ์ผ่านที่เสนอ (ต้องให้ Founder ยืนยัน) |
|---|---|---|
| Recall | ร้านใน ground truth ที่ provider คืนมาเมื่อค้นในรัศมี 1 กม. | ≥ 80% และร้านข้างทางไม่ต่ำกว่ากลุ่มอื่นมากนัก |
| Price availability | สัดส่วนร้านที่คืนค่าราคา | ≥ 60% จึงใช้ตัวกรองจาก provider ตรง ๆ ได้ ต่ำกว่านั้นใช้ชั้นข้อมูล KinNai (SP-01) |
| Price accuracy | เทียบราคาที่ provider ให้กับราคาจริงที่ผู้ทดสอบรู้ | ≥ 80% อยู่ในระดับงบเดียวกัน |
| Hours availability / accuracy | สัดส่วนที่มีเวลาเปิดและตรงกับความจริง | ≥ 70% |
| Cuisine | ประเภทตรงกับ 6 แนวของแอป (ข้าว เส้น อีสาน ญี่ปุ่น สุขภาพ อื่น ๆ) | ≥ 80% |
| Duplicates / ร้านปิดถาวร | นับจากตัวอย่าง | ≤ 5% |
| ต้นทุนจริงต่อการค้นหา | จากบิลทดสอบ | ตรงกับ §6 |

ตัวเลขเกณฑ์ผ่านเป็นข้อเสนอของผม ไม่ได้มาจากมาตรฐานใด

## 8. ข้อเสนอ

1. **ตอนนี้:** อ่านเอกสารฉบับเต็มของ Google (policy, ตารางราคา, data fields) และ Foursquare (Usage Guidelines, EULA) ด้วยตัวคุณเองหรือวางข้อความมาให้ผมตรวจ เพื่อปิดจุดที่แหล่งข้อมูลขัดกัน (SP-03)
2. **ก่อน Gate 2:** ทดสอบ §7 กับ Google, Foursquare และ Longdo
3. **ตัดสิน Q-001 ที่ Gate 2** ตามผลทดสอบ ถ้า Google ผ่านเกณฑ์ ให้ใช้ Google และทำชั้นข้อมูลราคาของ KinNai เป็นส่วนเสริม ถ้าไม่ผ่าน ให้พิจารณา Longdo ร่วมกับชั้นข้อมูล KinNai
4. **ใน PLAT-003:** ห่อ provider หลัง interface `searchPlaces(criteria)` เก็บเฉพาะ `place_id` ถาวร ตั้ง daily quota, budget alert และ kill switch
